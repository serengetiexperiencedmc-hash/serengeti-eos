## Problem statement

I4.33 records last-used DLQ stale-audit **preset** state and usage rows **in memory only**. A process restart loses both. I4.29 last-used **filter** and I4.31/I4.32 named **presets** already dual-write and hydrate under ADR-0017. I4.31 deferred “Persist last-used preset usage”. I4.33 closed the in-memory gap and left persist undefined.

I20.22 already closed the same persist gap for recommend-audit preset usage. I4.34 applies that **behavioural** persist/hydrate pattern to the I4.33 DLQ collections. It uses its **own** I4 tables. It does not reuse `ai_recommend_stale_audit_export_preset_usage` or `ai_recommend_stale_audit_export_last_preset`. It does not add I3 usage tables. It does not invent I3.36, I20.23, or PG.30. It does not alter I4.29 last-filter persistence.

## Objective

When implementation is later authorized:

- Dual-write each I4.33 usage row and last-used preset when `store.dbPool` is set
- Hydrate both collections on API startup
- Keep I4.33 record/echo semantics (record only on successful named-preset apply; GET does not record or persist)
- Keep I4.29 last-used **filter** independent
- Keep I4.32 rename/delete semantics (snapshot names; no usage cleanup on delete; no FK)
- Stay inside ADR-0017 Dev/Test dual-write; in-memory remains Dev/Test read SoR

## Persistence lifecycle

Connect persist **only** from the existing I4.33 record path (`recordDlqStaleAuditExportPresetUsage` after a successful named-preset apply). Implementation may make that function `async` and `await` both persists, matching I20.22 (`persist usage` then `persist last preset`).

| Event | Memory (I4.33) | I4.34 persist | I4.29 lastFilter |
| --- | --- | --- | --- |
| Successful export **with** resolved preset | Append usage; upsert last preset | Await both persists when `dbPool` set | Existing await persist |
| Successful export **without** preset | No usage write | No usage / last-preset persist | Existing await persist |
| Missing / cross-tenant preset | No usage write (404) | None | None (export fails) |
| Invalid name / window | No usage write; no last-filter write | None | None |
| Status GET | Echo only | **None** | None |
| Usage GET (JSON/CSV) | Echo only | **None** | None |
| I4.32 rename | Preset name only; usage / last-preset snapshots unchanged | No rewrite of usage / last-preset rows | Unchanged |
| I4.32 delete | Preset removed; usage + last-preset rows remain | No delete of usage / last-preset | Unchanged |
| Persist query throws | Memory write already applied | Swallow; do not fail the HTTP 200 | Existing swallow |

| `store.dbPool` | Last filter (I4.29) | Preset (I4.31/I4.32) | Usage / last preset |
| --- | --- | --- | --- |
| unset | Memory only | Memory only | Memory only (I4.33) |
| set | Existing await persist | Existing await persist / persist-delete | **Await persist** (this increment) |
| query throws | Existing swallow | Existing swallow | Swallow (same class) |

In-memory remains Dev/Test read SoR (ADR-0017). **Not** production SoR. Does not create PG.30. Does not reopen ADR-0017.

## Hydration lifecycle

When `EOS_DATABASE_URL` is set, `apps/api/src/main.ts` already hydrates I4.29 last-filters and I4.31 presets. I4.34 adds two calls in that same startup block, after preset hydrate (so preset list and usage snapshots are independently merged):

1. `hydrateNotifDlqSlaDigestStaleAuditExportPresetUsages(pool, store)`
2. `hydrateNotifDlqSlaDigestStaleAuditExportLastPresets(pool, store)`

Proposed logs (I20.22 / I4.31 style):

- `i434_dlq_sla_digest_stale_audit_export_preset_usage_hydrate` `{ merged }`
- `i434_dlq_sla_digest_stale_audit_export_last_preset_hydrate` `{ merged }`

When `EOS_DATABASE_URL` is unset: no hydrate (existing `memory_only` warning). No new hydrate log.

Hydrate **does not** record new usage. Hydrate **does not** persist.

Merge rules:

- Usage: replace existing store row with same `id`, else push
- Last preset: replace existing store row with same `tenantId` + `principalId`, else push
- Do not drop in-memory rows that are absent from PG (same as I4.31/I20.22)

After hydrate, I4.33 list sort remains newest `createdAt` first for API `usages`.

## Acceptance criteria

- Persisted `lastPreset` survives restart (hydrate onto an empty store restores it)
- Persisted `usages` survive restart
- Tenant isolation on persist, hydrate, and API echo
- Principal isolation on persist, hydrate, and API echo
- Usage ordering: newest `createdAt` first on status / usage export
- `presetName` is a snapshot at apply time
- I4.32 rename does not rewrite historical usage / last-preset snapshots
- I4.32 delete does not remove usage / last-preset rows; deleted id still 404 on export
- Repeat apply appends another usage and refreshes last-preset persist
- Status GET and usage GET do not create records and do not persist
- I4.29 `lastFilter` remains independent and still persists on successful export
- No I3 usage persistence or I3 usage tables
- No I20 usage-table reuse
- No PG.30
- No production persistence architecture
- C1 Gate status unchanged
- I4.33 record/echo/API behaviour remains compatible
- I4.16–I4.34 tests pass; I3.35 and I20.22 increment strings unchanged
- Unsigned `/commercial/events` can show I4.34 / version banner after implementation
- No C2+, LLM, or autonomous apply

## Unresolved risks

- Persist-throw swallow leaves memory ahead of PG until the next successful persist (accepted I4.31 / I20.22 class).
- Hydrate resurrects last-preset / usage rows that point at an I4.32-deleted preset id (accepted I4.33 semantic; now durable). UI must not prefill a missing id. Do not add usage-cleanup.
- I4.31/I4.32 preset dual-write resurrection remains a separate accepted risk. I4.34 does not change preset hydrate.
- Live `EOS_DATABASE_URL` dual-write is not required of this preview. Implementation tests use a mocked pool unless a later instruction requires gated PG tests.

No blocking undecided schema or API question. Implementation must not invent I3/I20 tables or PG.30 if a persist detail is missing — follow I20.22 column mapping onto the I4 table names in this contract.
