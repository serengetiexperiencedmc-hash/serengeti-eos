## Problem statement

I4.30 added named tenant DLQ stale-audit export presets. I4.31 persists them. I4.32 adds rename/delete by id. I4.29 already persists the last-used **filter** (`action` / `since` / `until`).

Operators cannot see which **preset** they last applied, and there is no usage audit when export applies a named preset. I4.31 deferred “Persist last-used preset usage”. I4.32 kept that gap out of scope and kept I4.29 last-used **filter** unchanged.

I20.21 already closed the same in-memory gap for recommend-audit presets (I20.22 later persisted it). I4.33 applies that **behavioural** pattern to the I4.30–I4.32 DLQ store. It does not invent I3.36, I20.23, or PG.30. It does not add I3 allowlist usage tables (I3.35 excluded those). It does not reuse I20.21 / I20.22 tables.

---

## Objective

When implementation is later authorized:

- Record an in-memory usage row when a named DLQ stale-audit export preset is applied
- Stamp the last-used preset per tenant + principal
- Echo `lastPreset` and `usages` on status GET without recording usage
- Export JSON/CSV of the caller’s usage rows
- Prefill the Events preset select from `lastPreset` when that id still exists
- Keep I4.29 last-used **filter** behaviour
- Stay inside ADR-0017 Dev/Test in-memory read SoR — **no persist in this increment**

## API changes

| Method | Path | Perm | Behaviour |
| --- | --- | --- | --- |
| `GET` | `/v1/notifications/email/dlq-sla-digest-status` | `notification:read:email_outbox` | Echo `lastPreset` + `usages` (no record) |
| `GET` | `/v1/notifications/email/dlq-sla-digest-stale/export` | `notification:read:email_outbox` | If `preset` / `presetId` resolves, append usage and stamp last preset; always keep I4.29 `lastFilter` on successful export |
| `GET` | `/v1/notifications/email/dlq-sla-digest-stale/export/presets/usage` | `notification:read:email_outbox` | JSON/CSV usage export for the caller |

Unauthenticated → `401` `unauthenticated` (`principalFromAuthHeader`).

Existing I4.30–I4.32 list/upsert/rename/delete routes stay. After implementation, successful status / stale-export / usage-export bodies include `increment: "I4.33"`. Until then they remain `"I4.32"`.

### Status success (additions)

```
{
  "lastFilter": { … } | null,
  "lastPreset": { "presetId": "…", "presetName": "Last snoozes", "usedAt": "…" } | null,
  "usages": [ { "id": "…", "presetId": "…", "presetName": "Last snoozes", "createdAt": "…" } ],
  "presets": [ … ],
  "increment": "I4.33"
}
```

`lastPreset` and each usage row are sanitized: no `tenantId`, no `principalId`, no `createdByPrincipalId`.

### Export without a preset

200. `lastPreset` is the existing last-used preset or `null`. **No** new usage row. I4.29 `lastFilter` still updates.

### Export with a resolved preset

200. Append one usage row. Replace the caller’s last-used preset (`presetId`, `presetName` snapshot, `usedAt`). Return sanitized `lastPreset` + existing `preset` + `lastFilter`.

### Usage export success

JSON:

```
{
  "format": "json",
  "lastPreset": { … } | null,
  "usages": [ … ],
  "count": 1,
  "generatedAt": "…",
  "increment": "I4.33"
}
```

CSV: `presetId,presetName,createdAt` (same columns as I20.21). Also return `lastPreset`, `usages`, `count`.

Unknown `format` (not `json` / `csv` / omitted) → `400` `invalid_format`. Usage export does **not** record usage and does **not** persist.

## Record / echo rules

1. Authorize read (`notification:read:email_outbox`).
2. Resolve preset only when `preset` or `presetId` is present. Missing / other-tenant → `404` `preset_not_found`; **no** usage write.
3. Invalid name / window on export → existing I4.30 errors; **no** usage write; **no** last-filter write (I4.29 already requires successful export).
4. Successful export **without** a preset: I4.29 last-filter only; do not append usage.
5. Successful export **with** a preset: append usage; upsert last-used preset for `tenantId` + `principalId`; keep I4.29 last-filter.
6. Status GET and usage GET: echo only. Do not append usage. Do not persist.
7. Repeat export of the same preset: append another usage row; refresh last-used preset.
8. Usage rows snapshot `presetName` at apply time. I4.32 rename does **not** rewrite historical usage names. I4.32 delete does **not** remove usage rows or the last-used preset row.
9. After delete: export with that `presetId` still `404` (I4.32); no new usage. Status may still echo a last-used preset whose id is gone. UI must not prefill a missing id.

## Store (in-memory only)

Proposed collections (names are proposed; implementation may match these):

- `notifDlqSlaDigestStaleAuditExportPresetUsages`
- `notifDlqSlaDigestStaleAuditExportLastPresets`

| Collection | Identity |
| --- | --- |
| Usages | `id` (new UUID per apply); filter list by `tenantId` + `principalId`; sort newest `createdAt` first |
| Last preset | One row per `tenantId` + `principalId` |

Do **not** write these to PostgreSQL in I4.33. `store.dbPool` set or unset must not dual-write usage / last preset. No new migration. No hydrate log.

## Authorization rules

| Operation | Permission | `authorize` action |
| --- | --- | --- |
| Status GET (echo) | `notification:read:email_outbox` | existing `read:dlq_sla_digest_status` |
| Stale export (may record) | `notification:read:email_outbox` | existing export read action |
| Usage export | `notification:read:email_outbox` | `read:dlq_sla_digest_stale_audit_export_preset_usage` |

Deny → `{ error: "forbidden", reason }`.  
**403 fixture:** **Bob** (no `notification:read:email_outbox` and no dispatch). Do not use Alice (Alice has both).

Not `ai:read:recommend`. Not `ai:write:draft`.

## Tenant isolation

- Usage and last-preset lookup is `tenantId === principal.tenantId` **and** `principalId === principal.id`
- Other-tenant preset id on export → `404` `preset_not_found`; no usage write
- Usage export returns only the caller’s rows
- Do not leak `tenantId` / `principalId` on sanitized views
