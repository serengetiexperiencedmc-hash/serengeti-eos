## Problem statement

I3.33 added named tenant allowlist stale-audit export presets. I3.34 persists them. I3.35 adds rename/delete by id. I3.32 already persists the last-used **filter** (`action` / `since` / `until`).

Operators cannot see which **preset** they last applied, and there is no usage audit when export applies a named allowlist preset. I3.34 deferred “Persist last-used preset usage”. I3.35 kept usage out of scope and forbade adding I3 usage tables **in I3.35**.

I20.21 and I4.33 already closed the same **in-memory** gap for recommend-audit and DLQ presets. I3.36 applies that **behavioural** pattern to the I3.32–I3.35 allowlist store. It uses its own I3 in-memory collections. It does not reuse I4.33/I4.34 or I20.21/I20.22 tables. It does not invent I3.37, I20.23, PG.30, or I4.35. It does not alter I3.32 last-used **filter** persistence. It does **not** implement I3.34’s deferred persist item.

## Objective

When implementation is later authorized:

- Record an in-memory usage row when a named allowlist stale-audit export preset is applied
- Stamp the last-used preset per tenant + principal
- Echo `lastPreset` and `usages` on status GET without recording usage
- Export JSON/CSV of the caller’s usage rows
- Prefill the Notifications preset select from `lastPreset` when that id still exists
- Keep I3.32 last-used **filter** behaviour
- Stay inside ADR-0017 Dev/Test in-memory read SoR — **no persist in this increment**

Kernel types are proposed. Persist is **not** in this increment.

### Usage row

| Field | Notes |
| --- | --- |
| `id` | New UUID per successful named-preset apply |
| `tenantId` | Isolation (omitted from sanitized API view) |
| `principalId` | Isolation (omitted from sanitized API view) |
| `presetId` | Snapshot of applied preset id |
| `presetName` | Snapshot at apply time |
| `createdAt` | Apply timestamp |
| `createdByPrincipalId` | Operator who applied (omitted from sanitized API view) |

### Last-used preset

| Field | Notes |
| --- | --- |
| `tenantId` | Part of identity |
| `principalId` | Part of identity |
| `presetId` | Last successfully applied id |
| `presetName` | Snapshot at last apply |
| `usedAt` | Last apply timestamp |

One in-memory row per `(tenantId, principalId)`. Sanitized API view omits `tenantId` / `principalId`.

**No foreign key** and **no PostgreSQL table**. I3.35 delete must not remove usage / last-preset memory rows.

## API changes

| Method | Path | Perm | Behaviour |
| --- | --- | --- | --- |
| `GET` | `/v1/notifications/email/allowlist-dual-digest-status` | `notification:read:email_outbox` | Echo `lastPreset` + `usages` (no record) |
| `GET` | `/v1/notifications/email/allowlist-dual-digest-stale/export` | `notification:read:email_outbox` | If `preset` / `presetId` resolves, append usage and stamp last preset; always keep I3.32 `lastFilter` on successful export |
| `GET` | `/v1/notifications/email/allowlist-dual-digest-stale/export/presets/usage` | `notification:read:email_outbox` | JSON/CSV usage export for the caller |

Unauthenticated → `401` `unauthenticated`.

Existing I3.33–I3.35 list/upsert/rename/delete routes stay. After implementation, successful status / stale-export / usage-export / preset bodies that already emit an I3 increment string use `increment: "I3.36"`. Until then they remain `"I3.35"`.

No unrelated routes.

### Status success (additions)

```
{
  "lastFilter": { … } | null,
  "lastPreset": { "presetId": "…", "presetName": "Last snoozes", "usedAt": "…" } | null,
  "usages": [ { "id": "…", "presetId": "…", "presetName": "Last snoozes", "createdAt": "…" } ],
  "presets": [ … ],
  "increment": "I3.36"
}
```

`lastPreset` and each usage row are sanitized: no `tenantId`, no `principalId`, no `createdByPrincipalId`.

### Export without a preset

200. `lastPreset` is the existing last-used preset or `null`. **No** new usage row. I3.32 `lastFilter` still updates.

### Export with a resolved preset

200. Append one usage row. Replace the caller’s last-used preset (`presetId`, `presetName` snapshot, `usedAt`). Return sanitized `lastPreset` + existing `preset` + `lastFilter`.

### Usage export success

JSON:

```
{
  "format": "json",
  "lastPreset": { … } | null,
  "usages": [ … ],
  "count": 1,
  "generatedAt": "…",
  "increment": "I3.36"
}
```

CSV: `presetId,presetName,createdAt` (same columns as I20.21 / I4.33). Also return `lastPreset`, `usages`, `count`.

Unknown `format` (not `json` / `csv` / omitted) → `400` `invalid_format`. Usage export does **not** record usage and does **not** persist.

## Behavioral contract

| Event | I3.36 memory | I3.32 `lastFilter` |
| --- | --- | --- |
| Export **with** resolved preset | Append usage + update last preset | Existing persist |
| Export **without** preset | No I3.36 write | Existing persist |
| Missing / cross-tenant preset | 404; no usage | None (export fails) |
| Invalid name / window | No usage | None |
| Status GET | Echo only | No write |
| Usage GET | Echo only | No write |
| I3.35 rename | Historical usage snapshots unchanged | Unchanged |
| I3.35 delete | Usage / last-preset remain; deleted preset cannot be applied | Unchanged |

## Record / echo rules

1. Authorize read (`notification:read:email_outbox`).
2. Resolve preset only when `preset` or `presetId` is present. Missing / other-tenant → `404` `preset_not_found`; **no** usage write.
3. Invalid name / window on export → existing I3.33 errors; **no** usage write; **no** last-filter write (I3.32 already requires successful export).
4. Successful export **without** a preset: I3.32 last-filter only; do not append usage.
5. Successful export **with** a preset: append usage; upsert last-used preset for `tenantId` + `principalId`; keep I3.32 last-filter.
6. Status GET and usage GET: echo only. Do not append usage. Do not persist.
7. Repeat export of the same preset: append another usage row; refresh last-used preset. Newest `createdAt` first on API lists.
8. Usage rows snapshot `presetName` at apply time. I3.35 rename does **not** rewrite historical usage names. I3.35 delete does **not** remove usage rows or the last-used preset row.
9. After delete: export with that `presetId` still `404` (I3.35); no new usage. Status may still echo a last-used preset whose id is gone. UI must not prefill a missing id.

## Security / isolation

- Read gated by `notification:read:email_outbox`
- Unauthenticated → `401` `unauthenticated`

- Usage and last-preset lookup is `tenantId === principal.tenantId` **and** `principalId === principal.id`

- Usage export returns only the caller’s rows
- Sanitized responses omit `tenantId`, `principalId`, `createdByPrincipalId`

## Acceptance criteria

I3.36 is contractually satisfied only when implementation is later authorized **and**:

1. Successful named-preset application records an in-memory usage row
2. Successful named-preset application updates the in-memory last-used preset
3. Status GET echoes sanitized `lastPreset` and `usages`
4. Usage GET is read-only
5. GET / status / export-without-preset do not create I3.36 usage
6. Tenant and principal isolation is enforced
7. Historical `presetName` snapshots survive rename
8. Usage and last-preset survive preset deletion in memory
9. Deleted preset IDs cannot be reapplied (404)
10. Notifications does not prefill a missing preset
11. I3.32 `lastFilter` remains independent
12. No PostgreSQL persistence or hydration is introduced
13. No I4/I20 usage tables or behaviour is introduced
14. C1 remains unchanged and I3.36 is not C1 evidence
