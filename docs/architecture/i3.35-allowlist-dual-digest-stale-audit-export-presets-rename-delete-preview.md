## Problem statement

I3.33 added named tenant allowlist stale-audit export presets. I3.34 persists them. Operators can create or upsert by name, but they cannot rename or delete a preset without overwriting filter fields via upsert. I3.34 explicitly deferred “Rename / delete presets”. I20.20 already solved the same gap for recommend-audit presets.

I3.35 closes that I3.34 gap by mirroring I20.20 onto the I3.33/I3.34 allowlist preset store, using existing I0/I1 authorization and ADR-0017 dual-write. It does not invent I20.23 or PG.30.

## Scope

- Rename a tenant allowlist stale-audit export preset by id
- Delete a tenant allowlist stale-audit export preset by id
- Reuse I3.33 name normalization and I3.34 persist/hydrate tables
- Await persist on successful rename; await persist-delete on successful delete when `dbPool` is set
- Status GET continues to echo sanitized `presets` without persisting
- Commercial Notifications: **Rename preset** and **Delete preset** next to **Save preset**
- Map `conflict` → HTTP 409 on notification routes (I20 AI `sendError` already does this; I3 `sendError` currently does not)

I3.35 must use the existing I0 → I1 → I2 → I4 plane:

- **I0:** `authorize({ principal, permission, action })` before mutate; tenant from the authenticated principal

## Tenant-isolation requirements

- Lookup is `tenantId === principal.tenantId` **and** `id`
- A valid id from another tenant is `404` `preset_not_found` (no cross-tenant leak)
- Name clash is evaluated only inside the caller’s tenant
- Unique index `(tenant_id, lower(name))` already enforces this in PG
- Partner tenant `partner-demo` must not see or mutate `sedmc` presets

## Validation rules

Reuse `normalizeNotifAllowlistDualDigestStaleAuditExportPresetName`:

- Trim and collapse internal whitespace
- Empty / whitespace-only → invalid
- Length > 80 → invalid
- Rename payload is `{ name?: string }` only; `action` / `since` / `until` are not accepted on rename

## Error codes

| Condition | `error` | `reason` | HTTP |
| --- | --- | --- | --- |
| Missing/invalid session | `unauthenticated` | — | 401 |
| Missing write permission | `forbidden` | authorize reason | 403 |
| Empty / over-80 name | `invalid_request` | `invalid_name` | 400 |
| Unknown or other-tenant id | `not_found` | `preset_not_found` | 404 |
| Case-insensitive name owned by another preset in the same tenant | `conflict` | `name_taken` | 409 |

Notification `sendError` must treat `conflict` as 409 (copy I20 AI routes). Invalid rename/delete must not persist.

## Rename semantics

1. Authorize write.
2. Normalize `name`. Fail `invalid_name` without store write.
3. Find by `presetId` in the caller tenant. Missing → `preset_not_found`.
4. Find by normalized name in the same tenant. If another row (`clash.id !== existing.id`) → `name_taken`.
5. Same-id case-only rename is allowed (self is not a clash).
6. Keep `id`, `tenantId`, `createdAt`, `createdByPrincipalId`, `action`, `since`, `until`.
7. Set `name` and `updatedAt`.
8. Replace the in-memory row.
9. Await persist (I3.34 upsert-by-id). Unique `(tenant_id, lower(name))` remains valid.
10. Return sanitized preset + tenant preset list.

Rename does not upsert filter fields and does not record a recommend run.

## Delete semantics

1. Authorize write.
2. Find by `presetId` in the caller tenant. Missing → `preset_not_found`.
3. Remove the row from the in-memory collection (hard delete).
4. Await persist-delete by `id` when `dbPool` is set.
5. Return remaining sanitized tenant presets.

After delete:

- List/status omit the row
- Export with that `preset` / `presetId` → `404` `preset_not_found` (existing I3.33 apply rules)
- No I20.21/I20.22 usage or last-preset rows exist on I3; do not add them

## Persistence behaviour

No new migration. Reuse `074_i334_allowlist_dual_digest_stale_audit_export_preset.sql`.

| Operation | PG |
| --- | --- |
| Rename | Existing I3.34 `INSERT … ON CONFLICT (id) DO UPDATE` (name + `updated_at`) |
| Delete | `DELETE FROM notif_allowlist_dual_digest_stale_audit_export_preset WHERE id = $1` (I20.20 pattern) |

Hydrate-on-startup stays I3.34 (`merge` by `id`). Failed dual-write is try/catch, same as I3.34 / I20.20 (“fire-and-forget” after the in-memory write). In-memory remains Dev/Test read SoR (ADR-0017).

## Database-pool behaviour

| `store.dbPool` | Rename | Delete |
| --- | --- | --- |
| unset | Memory only; persist no-ops | Memory only; persist-delete no-ops |
| set | Await upsert | Await delete-by-id |
| query throws | In-memory result still returned; persist error swallowed | Same |

Invalid name, 404, and 409 must not call persist.

## UI behaviour (`/commercial/notifications`)

Add **Rename preset** and **Delete preset** beside **Save preset** (I20.20 AI Drafts layout).

- Rename: enabled when a preset id is selected and the name field is non-empty; POST rename; refresh `presets`; keep selection on the same id; show `Saved`/`Renamed` style status
- Delete: enabled when a preset id is selected; DELETE; refresh `presets`; clear selected id and name
- Selecting a preset still fills action / since / until (I3.33)
- Save preset remains I3.33 upsert-by-name
- Unsigned page: banner/eyebrow only; no credentialed click in shared CRM
