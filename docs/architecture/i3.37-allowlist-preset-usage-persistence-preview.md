## 9. Data model

Kernel types in `packages/kernel/src/notification-email.ts` stay. Persist maps the existing I3.36 shapes onto **new I3 tables**.

These table names are an **I3 decision**. They continue the I3.32 / I3.34 prefix `notif_allowlist_dual_digest_stale_audit_export_*`. They are **not** I4.34 or I20.22 tables.

### 9.1 Usage table

**Exact name:** `notif_allowlist_dual_digest_stale_audit_export_preset_usage`

| I3.36 field | Column | Type | Notes |
| --- | --- | --- | --- |
| `id` | `id` | UUID | **Primary key.** New UUID per successful named-preset apply |
| `tenantId` | `tenant_id` | UUID NOT NULL | Isolation |
| `principalId` | `principal_id` | UUID NOT NULL | Isolation |
| `presetId` | `preset_id` | UUID NOT NULL | Snapshot of applied preset id — **not** a live FK |
| `presetName` | `preset_name` | TEXT NOT NULL | Snapshot at apply time |
| `createdAt` | `created_at` | TIMESTAMPTZ NOT NULL | Apply timestamp |
| `createdByPrincipalId` | `created_by_principal_id` | UUID NOT NULL | Operator who applied |

Sanitized API view still omits `tenantId`, `principalId`, `createdByPrincipalId`.

**Tenant/principal uniqueness:** none on usage. Repeat apply appends another row. Lists are filtered by `tenant_id` + `principal_id` and ordered newest `created_at` first at the API.

### 9.2 Last-used-preset table

**Exact name:** `notif_allowlist_dual_digest_stale_audit_export_last_preset`

| I3.36 field | Column | Type | Notes |
| --- | --- | --- | --- |
| `tenantId` | `tenant_id` | UUID NOT NULL | Part of PK |
| `principalId` | `principal_id` | UUID NOT NULL | Part of PK |
| `presetId` | `preset_id` | UUID NOT NULL | Last successfully applied id (snapshot) |
| `presetName` | `preset_name` | TEXT NOT NULL | Snapshot at last apply |
| `usedAt` | `used_at` | TIMESTAMPTZ NOT NULL | Last apply timestamp |

**Primary key / uniqueness:** `(tenant_id, principal_id)` — one last-used preset per tenant + principal. This matches I3.36 (“one row per `tenantId` + `principalId`”) and the I3.32 last-filter PK shape for a different entity.

Sanitized API view still omits `tenantId` / `principalId`.

### 9.3 Snapshot vs preset-table reference

Usage and last-preset rows **intentionally remain snapshot-based**. They store `preset_id` and `preset_name` as values copied at apply time. They do **not** reference `notif_allowlist_dual_digest_stale_audit_export_preset` as a live relation.

I3.36 already snapshots `presetName` and keeps usage / last-preset after I3.35 delete. A live reference would redesign that.

### 9.4 Foreign-key and delete/cascade policy

**No foreign key** to `notif_allowlist_dual_digest_stale_audit_export_preset`.

| Alternative | Why rejected |
| --- | --- |
| `ON DELETE CASCADE` | Would delete usage / last-preset when I3.35 deletes a preset. Violates I3.36. |
| `ON DELETE RESTRICT` / `NO ACTION` | Would block I3.35 delete or fail persist-delete. Reopens I3.35. |
| FK without delete clause | Still couples I3.37 rows to preset existence and can fail hydrate/delete. |

**Delete/cascade behaviour:** none. No `ON DELETE` clause. I3.35 `persistDeleteNotifAllowlistDualDigestStaleAuditExportPreset` stays **preset-table only**.

**Does deleting an I3.35 preset delete usage rows?** **No.** Usage rows remain. Last-preset rows remain. Do not add usage-cleanup because persistence is being added.

**Historical `presetName`:** stored on the usage / last-preset row at apply time. I3.35 rename updates the preset table only. I3.37 must **not** `UPDATE` usage or last-preset names on rename.

No extra indexes this increment.

## 11. Persistence lifecycle

### 11.1 Helper names and responsibilities

Place persist/hydrate in `apps/api/src/persistence/notifications.ts` (I3.32 / I3.34 home). Place SQL in `apps/api/src/persistence/pg-repository.ts`. Do **not** add I3 helpers to I4 or I20 persistence modules.

| Helper | Responsibility |
| --- | --- |
| `insertNotifAllowlistDualDigestStaleAuditExportPresetUsage` | `INSERT` one usage row |
| `loadNotifAllowlistDualDigestStaleAuditExportPresetUsages` | `SELECT` all usages, `ORDER BY created_at ASC` (API re-sorts newest first) |
| `upsertNotifAllowlistDualDigestStaleAuditExportLastPreset` | `INSERT … ON CONFLICT (tenant_id, principal_id) DO UPDATE` `preset_id` / `preset_name` / `used_at` |
| `loadNotifAllowlistDualDigestStaleAuditExportLastPresets` | `SELECT` all last-preset rows |
| `persistNotifAllowlistDualDigestStaleAuditExportPresetUsage` | no-op if `!pool`; try/catch swallow (I3.32 / I3.34 fire-and-forget) |
| `persistNotifAllowlistDualDigestStaleAuditExportLastPreset` | no-op if `!pool`; try/catch swallow |
| `hydrateNotifAllowlistDualDigestStaleAuditExportPresetUsages` | merge by `id`; return newly pushed count |
| `hydrateNotifAllowlistDualDigestStaleAuditExportLastPresets` | merge by `tenantId` + `principalId`; return newly pushed count |

There is **no** persist-delete helper for usage or last-preset.

### 11.2 When to persist

Connect persist **only** from the existing I3.36 record path (`recordAllowlistStaleAuditExportPresetUsage` after a successful named-preset apply). Implementation may make that function `async` and `await` both persists: usage first, then last-preset.

| Event | I3.36 memory | I3.37 persist | I3.32 lastFilter |
| --- | --- | --- | --- |
| Successful export **with** resolved preset | Append usage; upsert last preset | Await both persists when `dbPool` set | Existing await persist |
| Successful export **without** preset | No usage write | No usage / last-preset persist | Existing await persist |
| Missing / cross-tenant preset | No usage write (404) | None | None (export fails) |
| Invalid name / window | No usage write; no last-filter write | None | None |
| Status GET | Echo only | **None** | None |
| Usage GET (JSON/CSV) | Echo only | **None** | None |
| I3.35 rename | Preset name only; usage / last-preset snapshots unchanged | No rewrite of usage / last-preset rows | Unchanged |
| I3.35 delete | Preset removed; usage + last-preset rows remain | No delete of usage / last-preset | Unchanged |
| Repeat named-preset apply | Append another usage; refresh last preset | Second usage INSERT; last-preset upsert | Existing await persist |

| `store.dbPool` | Last filter (I3.32) | Preset (I3.34/I3.35) | Usage / last preset |
| --- | --- | --- | --- |
| unset | Memory only | Memory only | Memory only (I3.36) |
| set | Existing await persist | Existing await persist / persist-delete | **Await persist** (this increment) |
| query throws | Existing swallow | Existing swallow | Swallow (same I3 class) |

### 11.3 Atomicity and transactions

**Usage writes are not a SQL transaction** with last-preset or with I3.32 last-filter.

**Last-preset upsert and usage insert are independently persisted** (two helper calls). Justification: I3.36 already performs two in-memory writes; I3.32 last-filter is already a third independent persist; I3 persist helpers swallow per call. A new multi-statement transaction would be a new I3 persistence architecture and is **not** introduced here.

Accepted consequence: usage may persist while last-preset persist is swallowed, or the reverse. Memory remains Dev/Test read SoR (ADR-0017).

**No dual-write** to `notif_dlq_sla_digest_stale_audit_export_preset_usage` / `_last_preset` or `ai_recommend_stale_audit_export_preset_usage` / `_last_preset`.

## 12. Hydration lifecycle

When `EOS_DATABASE_URL` is set, `apps/api/src/main.ts` already hydrates I3.32 last-filters and I3.34 presets. I3.37 adds two calls in that same startup block, **after** allowlist last-filter hydrate and **after** allowlist preset hydrate:

1. `hydrateNotifAllowlistDualDigestStaleAuditExportPresetUsages(pool, store)`
2. `hydrateNotifAllowlistDualDigestStaleAuditExportLastPresets(pool, store)`

Order justification (I3 decision, not FK order): presets and usage snapshots are independent. Hydrating usage / last-preset after presets keeps the existing I3 allowlist block together and still allows a last-preset whose preset id is gone (I3.36).

Proposed logs (I3.32 / I3.34 style):

- `i337_allowlist_dual_digest_stale_audit_export_preset_usage_hydrate` `{ merged }`
- `i337_allowlist_dual_digest_stale_audit_export_last_preset_hydrate` `{ merged }`

When `EOS_DATABASE_URL` is unset: no hydrate (existing `memory_only` warning). No new hydrate log.

### 12.1 Merge semantics

- **Usages:** match by `id`. Existing in-memory row is replaced. Missing id is pushed. Return count of newly pushed rows. Same merge class as I3.34 presets (by `id`).
- **Last-preset:** match by `tenantId` + `principalId`. Existing row is replaced. Missing pair is pushed. Return count of newly pushed rows. Same merge class as I3.32 last-filter (by tenant + principal).

After hydrate, I3.36 list sort remains newest `createdAt` first for API `usages`.

### 12.2 Hydration failure

Follow the existing I3.32 / I3.34 startup path: `await` the hydrate; do not invent a per-row swallow on `SELECT`. If the load throws, startup fails as it does today for other notification hydrates. Do not start with a silently empty usage store when PG was requested and the query failed.

## 14. Rename / delete semantics

Preserve I3.36 snapshot semantics. Persistence does **not** introduce cleanup.

**Rename**

- I3.35 rename updates the preset row only (memory + I3.34 table).
- Historical usage rows keep the original `presetName` / `preset_name`.
- Last-preset snapshot name is **not** rewritten by rename. It changes only on a later successful apply of the renamed preset (new snapshot).

**Delete**

- I3.35 delete removes the preset (memory + I3.34 persist-delete) only.
- Usage rows remain in memory and in the I3.37 usage table.
- Last-preset rows remain in memory and in the I3.37 last-preset table.
- Export of the deleted `presetId` still `404` `preset_not_found`; no new usage persist.
- Status / usage GET may still echo a last-preset whose id is gone.
- Notifications must **not** prefill a deleted / missing id.
